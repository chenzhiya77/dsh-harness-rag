## 1. 目标与范围

**要解决的问题**:今天的环是**静态的**。它把 `stages[]` 画成弧、把闸门通知长在工具卡上,但对"**这次 run 正走到哪**"一个字都不说 —— 一条跑了三分钟、绕了七八圈 tool→model 往返的 run,在环上看上去和刚起步一模一样。

**本期做**:让环在 run 进行中动起来 —— 一个**指针**沿环走,并累积**第几圈**;run 结束时停表。

**本期不做**:
- 不做历史 run 的脉冲**回放**(那是"跨 run 聚合/历史对比",§12 的非目标);
- **不把闸门通知搬上环**(§12#2 已裁:它们长在既有工具卡上);
- **不改**快照的 fetch-once 语义(见 §4 的第二条形状约束);
- 不新增路由、不新增顶级入口(§12.1 已裁:落点是头部栏触发器 + Dialog)。

## 2. 三个裁决点(**已全部裁定,2026-09-13**)

### D1 ⭐ 实时性从哪来?——**已裁 A(用户 2026-09-13,依据 Task 0 探针)**

> **定案:A(前端从既有 live 流推导,零后端改动)。** 用户先要求"先跑 Task 0 探针再定 D1",探针在三条真 run 上证明 A 的计数与 `llm_call_index` **逐条相等**(见 §7) ⇒ A 从"看起来可行"升级为"已验证可行"。**B(后端补阶段转换事件)降级为精化项**,只有在 §8 风险 1(三段近似)被真栈证明"用户分得出来"时才立项;**C 不做**。

上游 §12#6 写着"两个数据源,缺一不可",并说"通道是通的"。**2026-09-13 核实:那句话只对了一半。**

| 源 | 草图的说法 | 实际 |
|---|---|---|
| ⑧ 闸门运行时事件 | 第 1 项,另立 spec | **✅ 确实实时**:#1 已交付,**custom SSE 实时 + run_events 落库双发**(`middlewares/gate_events.py:66` / `:95-109`) |
| `llm_call_index` | "前端零消费者…**通道是通的**:与 `subagent.step` 分页回填同一个 `?event_types=` 机制" | **❌ 不实时**。它挂在 **journal 事件** `llm.ai.response` 的 `metadata` 上(`runtime/journal.py:487-507`),而 journal 的 `_put` **只落库、不做任何 stream publish**。全仓实时的 custom 发射者只有 **5 个**(`gate_events` / `llm_error_handling` / `safety_finish_reason` / `graph_search_tool` / `task_tool`),**不含它**。草图说的"通"是**分页回填**那条路,不是实时。 |

⇒ 于是有三条路,代价差别很大:

| | 方案 | 代价 | 得到的 |
|---|---|---|---|
| **A** | **前端从既有 live 流推导**:完成的 AI 响应数 ⇒ 圈数;"工具在飞" ⇒ `tools` 段;首个响应之前 ⇒ `intake`/`context`、末个响应之后 ⇒ `epilogue` 的**近似** | **零后端改动** | 圈数与指针都动;但 `intake`/`context`/`epilogue` 三段**说不准精确边界** |
| **B** | **后端补"阶段转换"的实时事件**(照 #1 的双发先例,约 2–3 个发射点:最外层 `before_agent` ⇒ intake、`before_model` ⇒ context、`after_agent` ⇒ epilogue;model/tools 两段由既有信号给) | 一处**非旁路**改动(中间件)+ 契约同步 | 五段都精确 |
| **C** | 不做实时:只呈现"已完成的那一份" | — | **与项名矛盾**(等于把本项降级成"事后投影") |

**我的推荐:先 A,把 B 记为精化项。** 理由:本项的全部产品价值是"**走到哪 + 第几圈**",A 用零后端风险就拿到了;B 多出来的精度只作用于 model **前后**那三段,而 run 的绝大多数时间花在 model↔tools 往返上。⇒ **但这是待裁点,不是定案**;若你更看重三段精确,选 B,我就把它当"非纯前端"来排期。

> **Task 0 探针已跑(2026-09-13),结论支持 A**:客户端按"**根命名空间的 distinct AI message id**"数,与 `llm_call_index` 在三条真 run 上**逐条相等**(2=2、2=2、1=1);把命名空间帧算进去会数成 4。规则与实测数据见 §7。⇒ **A 从"看起来可行"升级为"已验证可行"**;它剩下的唯一代价仍然是 §8 风险 1 那条(三段近似)。

### D2 指针的驱动规则(投影)——**已裁(用户 2026-09-13,按推荐)**

三件事要定,草图一件都没说:

1. **角度**:当前 stage 在环上的位置。几何是现成的 —— `core/constitution/geometry.ts` 的 `ringLayout(:107)` / `polarPoint(:75)` / `arcPath(:83)`,`RING_START_DEG = -90`、`RING_SPAN_DEG = spanDeg(5)`,指针与弧**同一坐标系**,不新造几何。
2. **"一圈"是什么** —— 这是本项最核心的定义,候选:
   - (a) 一圈 = **一次 model→tools 往返**(于是"第几圈"= 第几次工具往返,与 `llm_call_index` 同步增长);
   - (b) 一圈 = 跑完**环上五段**一次(于是圈数增长得慢得多,一次 run 常常不足一圈)。
   **推荐 (a)**:它让指针每圈都有可见的位移,圈数也直接回答"这活儿干了多久"。⇒ **已裁**:落成 **`lap` = 带 `tool_calls` 的根 AI 响应的条数**(最后那条纯文本回答不计一圈)。
3. **闸门事件在环上的处置**:**已裁"环上不重复"**(它们已长在工具卡上);"经过某段时显示被拦过几次"**不做**。

### D3 落点与 Dialog 关闭时的状态 —— **已裁(用户 2026-09-13,按推荐:只在 Dialog 内)**

环在**头部栏触发器的 Dialog** 里(§12.1 已裁)⇒ 脉冲是**同一个环上的叠加层**,不开新入口。**已裁**:Dialog 关着时**触发器不动**(不加小状态)——上游 §8 风险 5 那句"脉冲在头部触发器上给一个小状态"说的是**失败呈现**那条线,不是本项;而那条线最终把徽标放在了**内联**(已交付),所以两者不会抢位置,但本项也**不需要**先占触发器。

## 3. 已核实的前提(2026-09-13 代码核查,带行号)

- **环是纯绘制原语,所有文案走 props**(`constitution-ring.tsx:40-59`;`frontend/AGENTS.md` 的构成视图不变量 **(b)** 明写"教它自己去 `useI18n` 就是两档重新漂回一起")⇒ **脉冲必须以 props 进入,或作为同层兄弟**,不能教环自己取数。
- **几何齐备**:`geometry.ts` 的 `RING_VIEWBOX(17)` / `RING_RADIUS(20)` / `RING_BAND(22)` / `RING_START_DEG(24)` / `LOOP_TRACK_RADIUS(27)` = `118 + 20 + 8` / `OUTSIDE_BAND_RADIUS(29)` / `EXIT_STAGE_KEY(36)="epilogue"` / `polarPoint(:75)` / `arcPath(:83)` / `ringLayout(:107)`。**环道半径已存在**(今天用于 loop 弧),指针可以走同一条道。
- **闸门事件载荷**:`{type: <tag>, name, hook, action, changes}`(`gate_events.py:95-109`),`type` 既是 SSE 帧名也是消费方路由键;live 一路**永不改变执行**(失败只 `warning`)。
- **`llm_call_index` 不实时**(见 D1 的表);它在 journal 事件 `llm.ai.response` 的 `metadata` 里,**只在 `?event_types=` 分页回填上可读**。
- **快照侧**:`run.start` 的 `constitution` 已即时落库;前端是 run 作用域 fetch-once(见前端 spec)。
- **前端的 live 通道**共三条:`messages-tuple`(AI 增量 / 工具结果)、`values`(快照)、`custom`(闸门等自定义帧)。**子代理帧带命名空间**(`values|<ns>`),根消费者忽略——**这一点是 D1-A 的关键**:客户端计数 AI 响应时**必须**把子代理帧排除,否则圈数会与 `llm_call_index` 不一致(后者只数 lead 的响应:子代理回调里的 journal 被 `deerflow_loop_bound=True` 摘除)。

## 4. 设计骨架(D1–D3 裁定后细化)

- **数据层** `core/pulse/`(与 `core/delivery/`、`core/run-status/` 同构,薄一层):
  - `types.ts`:`PulseState`(当前 `stageKey` + `lap` + 可选 `gateMarks`);
  - `reduce.ts`:**纯函数**,把一条 live 事件折算成 `PulseState` 的下一个值(**本项唯一有判断逻辑的地方**,必须纯函数 + 单测);
  - `hooks.ts`:订阅(若 D1 选 A,复用既有的流;不新增查询)。
- **组件**:环上的一个 **marker 层**(绝不碰弧的绘制),位置由 `polarPoint` 给;圈数用一行文本(文案待 D 后冻)。
- **接线**:Dialog 打开时订阅;关闭即退订(**不常驻**)。
- **两条形状约束(上游 §12#6 写的,照办)**:
  1. 脉冲必须**沿环走 N 圈**,不是五格依次点亮 —— 这是环形布局存在的全部理由;
  2. 快照仍然是 **fetch-once**,**脉冲是第二条数据通道**,**不要把两者混成一次拉取**,否则会把 run 级**静态事实**当成流式数据处理。

## 6. 非目标

- 不做**历史回放**(过去某个 run 的脉冲重演);
- 做不**跨 run 聚合**(平均绕几圈、哪段最耗时);
- **不改** `run.end` / `RunRow.status` 的任何语义;
- **不引入**任何新的连接或轮询(只用既有的三条流);
- **不做**第 7 项(subagent 委派树)——那是本项之后的另一块,两者同框时的层数问题记在 §8。

## 7. Task 0 探针(**已完成 2026-09-13,结论见下**)

**做法**:私有 `:8099`(`DEER_FLOW_AUTH_DISABLED=1`,用户的 `:8001` 全程未碰)+ python 直接读 `/api/threads/{tid}/runs/stream` 的 SSE(与前端同一批帧),`stream_mode:["messages-tuple","values","custom"]` + **`stream_subgraphs: true`**(故意开,好一次同时看到根帧与命名空间帧)。跑了 **3 条真 run**(含子代理的;以及两条试图踩闸门的)。收尾:五条测试线程**按确定 id** 逐条删除并复核 404、私有实例停掉、脚本删掉。

**① 圈数保真度 —— 结论:可行,且规则被实测钉死(3/3 一致)**

| run | 根命名空间 distinct AI id | `llm_call_index` 最大值 | 含命名空间会数成 |
|---|---|---|---|
| 派 2 个子代理 | **2** | **2** | 2+1+1 = **4** ❌ |
| 派 2 个子代理(第二次) | **2** | **2** | 4 ❌ |
| 未派子代理 | **1** | **1** | 1 ✓ |

⇒ **规则两条,缺一不可**:
- **按 message id 去重**:同一次 LLM 响应被拆成大量 `AIMessageChunk`(实测**一条 run 里根帧 103 个 chunk 只对应 2 个 id**)⇒ **数帧毫无意义,必须数 distinct id**;
- **排除带命名空间的帧**(`messages|<ns>`,实测子代理的命名空间形如 `tools:<uuid>`):前端**不设** `stream_subgraphs`(`frontend/AGENTS.md` 明写"web 前端不请求 subgraph streaming"),所以它天然只看到根帧 —— 但**这一条必须写成显式规则并测住**,否则将来谁一开 `stream_subgraphs`,圈数就会多算。

**② custom 帧的次序与时延 —— 部分实测**:custom 帧**确实与消息帧交织**且及时(`task_started` 在相邻根消息帧后 **0.05s** 到达、距下一帧 **1.19s**;`task_running` 落在消息帧之间)。
**未测到**:某个**闸门 tag**(`read_gate`/`subagent_limit`…)本身的到达次序 —— 两次尝试都没触发(不存在的文件"创建"是允许的,所以 `write_file` 不踩闸门;要 3 个并行 task 也没让模型真在同轮发 3 个)。**不阻塞**:闸门帧走的是**同一个** `emit_custom_event` 通道,且 #1 的验收已经证明它在真栈上到达。

**③ `stream_replay_gap` —— 未能复现**(沿用本仓库既有结论:非法 id / 极旧 id / 未来 id 都只会得到完整回放,见 `[[project-local-dev-stack]]` 记的同一条)。⇒ 该行为**按设计规则处理**(§8 风险 2),不靠探针。


## 8. 风险与开放项

1. **A 的粗糙度是最大开放项**:`intake`/`context`/`epilogue` 三段只有近似归属。⇒ 真栈上若证明"用户其实分不出来",就把 B 永久降级为**不做**;若分得出来,B 立项。
2. **脉冲与 `stream_replay_gap`**:那条自愈路径会**全量重置并重取**;脉冲必须与它协调,不能出现"gap 后指针倒退却仍显示第 8 圈"。
3. **与第 7 项(subagent 委托树)的层数**:若委派树也画在环上,两者会**抢同一条圈道**。**待第 7 项时确认**。
4. **`custom` 通道的 IM 隔离**:`STREAM_MODES` 不含 `custom`(那是 #1 的结论)⇒ 脉冲**天然只到 Web**、IM 通道看不到;这不是缺陷,但要写明,免得以后有人以为漏了。
5. **不新增查询是硬约束**:若实现时发现必须新增一次拉取,先停下重开 D1 —— 那条约束是上游 spec 写的。
