# RAG 孤儿向量对账清扫（删除残留回收）—— 设计

**Status:** ✅ **全交付（2026-10-05）**——D1–D4 全裁（甲/甲/乙/甲）；Task 0–3 完成（后端 TDD + 接线 + 真栈 E2E），实测见配套 plan：[2026-10-04-rag-orphan-vector-sweep.md](../plans/2026-10-04-rag-orphan-vector-sweep.md)。

**本对一件事：给 Qdrant 侧补一条"回收通道"。** 删除链路的现行口径是"向量/文件清理失败仅记录日志、不中断级联"（RFC §5.3 条目 2）；2026-10-04 的缺口盘点确认：这些失败留下的孤儿向量**没有任何主动回收路径**——重删 404、全库重建不碰孤儿、只有换 embedding 宽度时旧代整删才顺带清掉。本对用"以业务库为准绳的对账清扫"回收孤儿；不改删除姿态、不新增删除记录、不动用户可见行为。

## 1. 现状与缺口（锚点）

- 删除吞错面：`knowledge_service.py:443-475`（文档级联，Qdrant 失败仅记录）、`:500-504`（重试擦除同姿态）、`:567-575`（库级联）、`_delete_wiki_entries`（条目向量同姿态）；切片删除与卡片向量清理同族（卡片创建路径为向量先于行，见 §2.2 例外）。
- 残留不可见：检索/读取按业务行 hydrate，残留点读不到；无用户可见影响，纯存储卫生问题。
- 无回收：`reindex.py:119-137` 仅对活行 upsert（"every live chunk"），不扫描孤儿；`dimension_migration.py:195-205` 的 `_drop_documents_that_left` 只服务迁移窗口（前后文档差集）；换宽度的切代整删是唯一顺带回收。
- 点 ID 与业务键（`vector_store.py:187-204`）：chunk `deerflow:kb-chunk:{chunk_id}`、entity `deerflow:kb-entity:{kb_id}:{name}`、wiki `deerflow:kb-wiki:{entry_id}`、card `deerflow:kb-manual-card:{card_id}`；payload 带 `kb_id`（有 payload 索引），可按库过滤滚动（`scroll_collection`）。

## 2. 方案

### 2.1 对账口径

逐库滚动四个集合（kb_id 过滤、分页）→ 用 payload 业务键回查业务行 → 判孤儿后先收集候选、复核一遍再删（两段式）→ 复用既有删除方法清点（`delete_chunks` / `delete_entities` / `delete_wiki_entries` / `delete_manual_cards`）。**不建任何新持久记录**；判据永远是"当下业务行是否存在"（幂等：跑两遍结果一致）。

### 2.2 写序前提

对账的安全性依赖"业务行先于向量写入"：若存在任何"向量先行"的写入路径，清扫会把在途点误当孤儿删掉。写序已核：chunks / entities / wiki 三路为行先行（`worker.py:664→439`、`graph/indexer.py:177→213`、`wiki/generator.py:299→302`）；cards 是例外——创建路径“embed → upsert → DB insert”向量先于行（`knowledge_service.py:941-950`），由上述两段式复核兜住。残余窗口如实登记：最坏情况卡片行落库而向量被清，表现为该卡从 wiki 检索静默缺席（重新开关可自愈）。

### 2.3 触发与并发（D2/D3）

见决策点。成本口径：每库一圈 = 四集合各一次分页滚动 + 按批的业务行回查；空库近零成本，大库随点数线性（一圈只读业务库 + 少量删除写）。

### 2.4 失败与可观测（D4）

清扫自身失败（Qdrant 不可用、业务库忙）：记日志、跳过该库、下轮重试；不改变任何业务数据。

## 3. 决策点（已裁 2026-10-04：D1=甲、D2=甲、D3=乙、D4=甲）

- **D1 清扫范围 = 甲：四集合全扫。** 四条腿共用同一种吞错姿态，一次循环全覆盖。未选：乙（仅 `kb_chunks`）、丙（chunks+entities）。
- **D2 触发方式 = 甲：自动（启动后 jitter 一次 + 周期；`rag.sweep_enabled` 默认开、`rag.sweep_interval_hours` 默认 24）。** 未选：乙（仅手动）、丙（甲+乙）——手动入口不做。
- **D3 并发姿态 = 乙：仅在“该库无在飞 worker 且无迁移”时清扫。** 多一道闸，防写序盲区误删。未选：甲（不设闸）。
- **D4 可观测 = 甲：仅日志（每轮删除计数 + failure 行）。** 未选：乙（加状态面）。

## 4. 硬约束

- 只删 Qdrant 点；绝不触碰业务行与文件；不新增持久记录（与 RFC 现状口径一致）。
- 幂等、可重复执行；中断后下一轮继续。
- 检索与写入路径零改动；不改变任何用户可见行为。
- 不阻塞事件循环，沿用仓库既有后台任务并发惯例；与迁移互斥（D3=乙 时）。
- 判据永不以 Qdrant 自身计数为准绳——业务库是唯一权威。

## 5. 验收

1. 单测：四集合孤儿点（构造无业务行的点）→ 清扫后消失；正常点全保留（清扫前后计数一致）。
2. 单测：单集合删除抛错 → 记录并继续其余集合；下一轮补齐。
3. 单测：候选复核——收集后、删除前出现业务行 → 不删（卡片创建竞态守护）；两段式跑两遍结果一致。
4. 单测（D3=乙）：该库有在飞任务或迁移 → 跳过并记录。
5. 真栈：隔离实例制残留（停 Qdrant → 删文档 → 起 Qdrant）→ 跑一轮清扫 → 残留清零；正常库与检索结果不变。
6. 门禁：后端 knowledge 面全量 + ruff check/format 双净。

## 6. 非目标

- 不新增删除记录/恢复材料（存量口径已定，不回头）；
- 不改删除吞错姿态、不给删除加 503 或重试队列；
- 不做前端与手动入口；
- 不做集合整体重建/压缩（迁移线职责）；
- 不在检索侧加任何读取守卫（RAGFlow 档已裁）。
