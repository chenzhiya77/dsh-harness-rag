# RAG 图谱路检索质量增强设计（二期补充 Spec）

> 状态：已落地（2026-08-11，plan `../plans/2026-08-10-rag-graph-quality.md` Task 1–4；D5 硬编排分格预算为未来评估项） · 日期：2026-08-10 · 范围：graph_search 证据选择与扩展控制、通道③移除、增量实体再归一 · 关联：主 spec `2026-08-07-rag-knowledge-base-design.md` §4.2 / §4.7（二期检索质量闭环）

## 1. 背景：现状缺陷清单（代码实证）

对一期图谱路在线检索（`deerflow/tools/builtins/graph_search_tool.py`）与离线索引（`deerflow/knowledge/graph/{extractor,normalizer,store,indexer}.py`）的代码走读，并与主流产品（Microsoft GraphRAG、LightRAG）对照后，确认以下五个缺陷/议题：

### 1.1 证据按拼接顺序硬截断，无相关性排序

候选 `chunk_ids` 按「边通道 → 节点通道（实体名字母序）→ 弹性反查」拼接，去重后 `rows[:evidence_limit]`（默认 8 条）截断（`graph_search_tool.py` L111–145）；`get_chunks_by_ids` 按传入 ID 序返回（`store.py` L252–260），即截断顺序 = 拼接顺序。后果：

- 直接命中实体的切片可能被间接邻居的边切片挤掉；
- 文档规模增长后，单一热门实体的 `source_chunk_ids` 可占满全部名额（GraphRAG 社区称之为"热门实体垄断预算"，见其 text unit 选择策略的已知缺陷）；
- 返回给模型的证据是"结构相关"而非"语义相关"。

### 1.2 扩展全量 BFS，无剪枝

1–2 跳扩展拉入每一跳的所有前驱+后继（`graph_search_tool.py` L97–107），高扇出枢纽实体（如"系统/数据库"类高频词）会把大量不相关邻居带入 `seen`，其切片进一步挤占证据名额。

### 1.3 跨切片别名实体不合并

归一化（alias fold + 0.92 余弦并查集）仅在**单切片抽取结果内**执行（`indexer.py` L116）；入库以 `uuid5(kb_id, name)` 为确定性 ID（`store.py` L26–31）。完全同名可合并，但不同切片中表面写法不同的别名（如 `Model`/`Models`）会成为两个图节点。这是切片级断点续跑设计的取舍，属于已知设计边界而非运行时 bug。

### 1.4 通道③（弹性反查）与节点通道召回集合重合

索引时 `backfill[chunk_id] = names` 与 `upsert_entities(chunk_id=...)` 源自同一份抽取结果（`indexer.py` L118–122），payload `entities` 标签与实体 `source_chunk_ids` 互为正反镜像；且③排在拼接队列末尾，先去重后截断，实际增量贡献趋近于零。注意：「提及但未抽取」的切片覆盖是向量路的职责，非图谱路缺陷。

### 1.5 「统一 rerank」表述需要形态澄清

主 spec §4.7 二期评估项"三路强制并行 + 统一 rerank"若被实现为"切片+实体+wiki 条目混池平铺排序"，会损失三路角色分工（wiki 是预消化成品而非证据、图谱含结构导航信息）。需要明确的形态约束，见 D5。

## 2. 主流产品对照结论

- **GraphRAG Local Search**：上下文按类型分格预算（实体描述/关系/社区报告/原文切片各占独立 token 预算），格内按实体优先级 + 关系密度排序；其 text unit 选择存在与本项目 1.1 同源的"垄断"缺陷，社区改进方向：每实体上限、轮询、按相似度加权配额、**保底+竞争**（推荐）。
- **LightRAG**：同样只做抽取内实体合并（1.3 同病）；双层检索以向量路兜住纯提及覆盖（印证 1.4 的分工结论）。
- 归纳出的设计原则：**图结构负责定候选池，语义负责排序选择，跨路按角色分配预算**。

## 3. 设计 D1：图谱证据选择重构

**目标**：图结构只定候选池，语义决定入选与顺序（hop 仅服务同分决胜与 A/B 实验）。修改范围集中在 `graph_search_tool.py` 的候选收集与截断段。

### 3.1 两级分数（各自职责，互不混用）

- **切片分**：候选池每条切片对 query 的语义相似度——全局一把尺子，与来源实体/边无关。默认用 embedding 余弦（候选向量已在 `kb_chunks`，对 query 做一次 dense embedding 即可，零额外外部调用）；候选数 > `rerank_threshold`（默认 12）时可选 `qwen3-rerank` 精排，`RerankerError` 降级为 embedding 序（沿用主 spec §4.4 降级哲学）。
- **实体分**：每个 seen 实体的相关性分，本质是"实体名+描述"的 embedding 与 query 的语义相似度——命中实体用 `kb_entities` 落地匹配时返回的余弦分（`query_entities` 的 `point.score`，已有；同一图实体被多个 query 实体命中时取**最大分**），邻居实体用 D2 语义剪枝时计算的 query 余弦（剪枝副产品，零额外成本）。实体分**不参与切片排序**，仅用于：① D2 扩展剪枝；② 保底名额超预算时决定 hop0 实体的出资顺序（见 3.2 溢出规则）；③ 调试/召回测试展示。

> 为什么实体分不参与切片排序：保底与竞争两阶段已覆盖其职责——hop0 实体由保底直接保护，实体间竞争交给纯切片分全局解决；再叠加实体权重只会引入不可解释的耦合。

### 3.2 两阶段选取：保底 + 竞争

1. **先去重再限流**：候选先按 `chunk_id` 去重（同一切片被边/节点/反查重复命中只留一份、只打一次分）；随后每源限流——每实体 ≤ `per_entity_cap`（默认 3）条、每边 ≤ `per_edge_cap`（默认 2）条、反查维持 `limit=20`，从源头防垄断。
2. **边的 hop 归属**：边的 hop = 两端实体 hop 的较小值（仅用于同分决胜与 `hop_penalty` 实验）。注意：连接两个命中实体的边切片是关系型问题的关键证据，但**不进入保底**（2026-08-10 已确认）——其文本天然同时含两端实体名，切片分通常足够高，可在竞争阶段自然上浮；若召回测试显示关系型问题缺证据，再评估为 hop0 边增设保底。
3. **阶段一·保底**：每个 hop=0 实体取其实体内切片分 top-`hop0_guarantee`（默认 2）条——保底只保证资格，出哪几条仍由切片分（与 query 的语义相关性）决定。**溢出规则（逐轮出资）**：若 hop0 实体数 × 保底数 > 总预算，按实体分降序、**每轮每个实体只出 1 条**，多轮循环直至预算耗尽或全部足额——保证每个直接命中实体至少 1 条（覆盖），高相关实体先拿到第 2 条（深度）；禁止瀑布式一次性出资（尾部实体会被剃光头）。同分按实体名字典序决胜（仅为测试确定性服务，不作实质排序依据）。不足额实体（切片数 < 当轮应出数）出了就完，预算自然流向后继者。
4. **阶段二·竞争**：保底完成后，全部剩余候选（各实体保底之外的切片、边切片、反查切片）**只按切片分全局排序**填充剩余名额——hop≥1 邻居已通过 D2 语义剪枝完成实体级相关性筛选，hop 不再携带额外信息，不重复惩罚；同分时按 `(hop, chunk_id)` 决胜（仅保确定性）。`hop_penalty` 降级为**默认 0 的实验参数**：召回测试期间用于 A/B 对比「纯切片分 vs 距离扣分」，数据无收益则移除。
5. **截断**：仅条数上限 `evidence_limit`（默认 8），排序后截断。**不做 token 预算**——切片大小在索引期已被切片器硬性约束（>1024 token 硬切，目标 512±256），条数上限已隐含上下文成本封顶（最坏 ≈ 8×1024，典型 ≈ 4k），token 预算属于冗余保险，省去以减少旋钮与测试面。

> 为什么竞争阶段只按切片分（与 D2 剪枝不重复）：D2 在**实体级**用语义剪枝归一了邻居的相关性（留下的都是 query 相关实体），hop 作为「相关性代理」的信息已被剪枝吸收，再按 hop 扣分属于重复惩罚；切片分是对「该切片与 query 相关性」的直接测量，优于 hop 这个间接代理。且切片分机器本就因保底 top-2 与每源限流而必须存在，竞争阶段只是复用，零新增成本。

### 3.3 参数标定

`per_entity_cap / per_edge_cap / hop0_guarantee / evidence_limit` 均为起始默认值，走 `config.yaml` 的 `rag.*` 命名空间；`hop_penalty` 默认 0、仅作召回测试 A/B 的实验参数。最终数值由召回测试 + recall@k 数据扫参标定，不在设计阶段拍死。

契约影响：`evidence` 项新增可选 `score` 字段（取当次打分通道的原始分——embedding 余弦或 reranker 分，仅同次结果内可比，供召回测试与前端调试展示）；`message` 文案格式不变；工具入参不变。

## 4. 设计 D2：扩展剪枝

**原则**：语义决定留不留，预算决定多不多，度数只决定是否允许继续扩散。

1. **语义剪枝（主）**：邻居实体向量已在 `kb_entities`，扩展时仅保留与 query 向量余弦 ≥ `neighbor_min_score`（默认 0.4，可配）的节点进入 `seen`——零额外 embedding 调用。
2. **节点总预算（兜底）**：`seen` 总规模 ≤ `max_expanded_nodes`（默认 25）；超出时按语义分截断。纯成本控制，与相关性无关。
3. **枢纽守护（度数降级为辅助）**：度数 > `hub_degree_threshold`（默认 50）的节点，仅当其自身通过语义阈值时才扩展其邻居——度数不再作为实体去留依据（避免误剪高相关热词），只防"枢纽带出一串邻居"。**hop0 命中实体豁免本规则**——落地阈值 0.3 低于 `neighbor_min_score` 0.4，用户直接问到的实体不应被自身高扇出卡住。

`hops` 语义不变（模型调用时决定 1 或 2）。空结果如实返回的既有契约不变（缺邻居 → 如实答"未找到"）。

## 5. 设计 D3：增量全局实体再归一

**时机**：`index_document_graph` 文档级索引完成后触发；另留 cron 全量入口（远期）。

**范围**：本次 `touched_entities` + 其一跳邻居；图规模 < `full_scan_threshold`（默认 500 实体）时直接全表。

**算法**：复用 `normalizer.py` 的并查集逻辑（`_alias_key` 表面折叠 + 名称向量余弦 ≥ 0.92）。

**副作用链**（按实体组事务，全部幂等）：

1. `graph_entities`：代表名保留（先见优先），description 片段去重追加， `source_chunk_ids` 并集，被合并行删除；
2. `graph_relations`：端点重写为代表名，同 `(source, target, relation)` 合并（复用 store upsert 逻辑），合并产生的自环丢弃；
3. `kb_entities`：被合并实体向量删除，代表名按合并后 description 重 embed；
4. 切片实体标签双写重写：业务库 `chunks.entities` 列与 `kb_chunks` payload `entities` 同步把别名替换为代表名（后者复用 `set_chunk_entities`）——两者互为镜像，必须一起改；
5. wiki：受影响条目标 dirty（复用 `mark_dirty_for_titles`），由既有增量刷新链路消化。

**降级**：再归一失败不阻断索引主流程——记录日志并在文档 `error` 字段追加 `entity-resolution failed` 子标记（沿用"graph degraded"同款显式可见原则，绝不静默）。

## 6. 设计 D4：通道③移除

**决策：移除**（2026-08-10 定稿）。原“防御性冗余”定位经推演不成立：

1. ③的输出仅 `chunk_id`，原文仍需回业务库 `chunks` 表——业务库故障时③同样瘫痪；
2. ③的输入 `seen` 依赖 `kb_entities` 匹配与图表扩展——图表损坏时③连查询条件都构造不出；
3. 唯一能“兜底”的场景是 `source_chunk_ids` 与 payload 不一致的数据中间态——那应走数据修复，不应由查询路径长期背补丁。

**实证重复**：payload `entities` 标签与实体 `source_chunk_ids` 源自同一份抽取结果（互为镜像），③排在拼接队列末尾、先去重后截断，增量贡献为零；且每次 graph_search 都多付一次 Qdrant scroll 往返。

**删除边界**：

| 删除 | 保留 |
|---|---|
| `graph_search_tool.py` 候选收集第 4 步的 `scroll_chunks_by_entities` 调用（随 Task 1 一并执行） | `kb_chunks` payload `entities` 标签的索引期回写（切片可视化抽屉展示“关联实体”依赖；也是未来提及标注的地基） |
| `vector_store.scroll_chunks_by_entities` 方法（Grep 确认无其他调用方后） | payload 上的 `entities` KEYWORD 索引（过滤能力保留） |

**回退路径**：若召回测试数据显示节点通道（②）在真实 query 集上存在覆盖缺口，回补方向不是恢复③，而是做“真提及标注”（索引期轻量 NER/关键词匹配写入 payload）——让反查真正覆盖“提及但未抽取”的盲区，这是新机制而非③的复活。

## 7. 设计 D5：硬编排形态约束（主 spec §4.7 二期评估的设计输入）

对"三路强制并行 + 统一 rerank"的实现形态立约：

- **约束形态：分格预算**——各路内部对同类候选精排；跨路按角色分配 token 预算（向量切片 / 图谱证据+结构描述 / wiki 成品各占独立格子，互不竞争）；最终由模型综合。
- **禁止形态：混池平铺**——不允许把三路产物混入单一分数池统一排序截取（wiki 条目是答案成品、图谱含导航结构，与切片比"相关性分数"天然错位）。
- 评估方法不变：依赖召回测试 + recall@k 评测数据决定是否做硬编排、做到什么程度；本节约束只限定"做的时候按什么形态做"。

## 8. 实施顺序与验证策略

| Task | 内容 | 依赖 | 验证 |
|---|---|---|---|
| 1 | D1 证据选择重构（含通道③调用移除） | 无（自包含） | 单测覆盖去重限流/两阶段排序/保底溢出/条数截断；revert→RED→restore→GREEN 回归 |
| 2 | D2 扩展剪枝 | 无 | 单测覆盖语义阈值/节点预算/枢纽守护（含 hop0 豁免） |

| 4 | D4 方法清理：`scroll_chunks_by_entities` 无调用方确认后删除 | Task 1 | Grep 全局无引用 + 全量测试通过 |

- 全部 Task 遵循三路索引既有 TDD 范式（契约先行 → RED → GREEN → 回归验证 → live/边界兜底）。
- Task 1–3 与召回测试 API **无先后依赖**，可并行推进；上线后用 recall@k 对比改造前后数据，为 D5 决策供数，并观察 D4 移除后节点通道（②）的覆盖变化（若出现缺口，按 §6 回退路径做真提及标注）。
- 所有新增参数走 `config.yaml` 的 `rag.*` 命名空间，默认值如上，保持一期行为可通过配置近似还原（限流设大、阈值设 0）。

## 9. 风险与回退

| 风险 | 缓解 |
|---|---|
| D1 reranker 抖动增加延迟 | 默认 embedding 序，reranker 为可选增强 + 既有降级通道 |
| D2 语义阈值误剪导致图路空返回 | 阈值可配；空结果如实返回契约不变；向量路天然兜底（§4.4） |
| D3 误合并损坏图谱 | 高阈值 0.92；只追加不删除 description；操作幂等可重跑；cron 全量校正兜底 |
| 一期行为回归 | 配置默认值保证可近似还原一期行为；改造前后 recall@k 数据对比验收 |
